# 多用户隔离与权限模型设计评审稿 V0.2

> 状态：**已评审并落地（V56–V57，2026-11-10）**，实施与验收记录见《交付验收报告.md》V56（后端与安全边界）与 V57（用户管理页面）。
> 设计原则：**知识库与向量全局共享；用户会话私有；后端强制鉴权；前端仅做体验隐藏。**

## 1. 现状与差距

当前实现状态：

- 数据库表：`document`、`document_chunk` 为全局文档与切片；`chat_session` 无用户归属；`chat_record` 经 `session_id` 关联会话。
- 后端路由：文档上传/列表/删除、会话增删查、聊天 SSE 均未做认证与角色校验。
- 前端：无登录态；`useChat.js` 只管理当前浏览器会话列表；`DocsView.vue` 直接暴露文档管理操作。
- 检索链路：`rag.retrieve()` 全局检索公共向量，知识库内容天然共享。

主要差距：

1. 缺少用户身份与登录态。
2. 缺少会话私有归属与越权访问校验。
3. 缺少管理员/普通用户权限边界。
4. 缺少操作审计与禁用账号能力。

## 2. 设计目标与非目标

### 2.1 目标

1. **知识库公用**：所有登录用户共享同一套文档、切片与向量检索结果；普通用户检索到的来源数据不按用户隔离。
2. **管理员可管理配置与知识库**：管理员可上传/删除文档、重解析文档、重建索引、查看系统信息、管理账号。
3. **普通用户管理自己的会话**：每个用户可创建多个私有会话，查看、重命名、删除自己的会话，并继续在会话内多轮问答。
4. **会话与聊天记录隔离**：普通用户 A 不可见、不可访问、不可删除普通用户 B 的会话与历史记录。
5. **后端强制权限**：即使绕过前端调用接口，后端仍必须拒绝越权操作；前端按钮隐藏不作为安全控制。
6. **兼容现有能力**：现有单文件/批量上传、检索、Rerank、SSE、文档删除等链路保留。

### 2.2 非目标（本轮设计不覆盖）

- 不做私有文档库、文档级 ACL、按用户独立向量库。
- 不做 OAuth/OIDC、LDAP、SSO、企业微信/钉钉登录。
- 不做细粒度 RBAC、部门权限、项目空间、群组协作。
- 不做聊天内容公开分享、消息转发、消息批注。
- 不做异步任务队列、分布式部署、在线协作编辑。
- 不做端到端加密；本地 Demo 不引入复杂密钥管理。

## 3. 角色定义

| 角色 | 说明 | 核心能力边界 |
| --- | --- | --- |
| 匿名用户 | 未登录或登录态失效用户 | 只能打开登录页；不能发起问答、不能查看会话、不能管理知识库 |
| 普通用户 member | 日常问答用户 | 管理自己的会话；使用全局知识库检索；不可上传/删除/重解析文档，不可重建索引，不可管理用户 |
| 管理员 admin | 知识库与系统运维负责人 | 具备 member 全部能力；可管理文档、执行重解析/索引重建、查看系统信息、创建/禁用/重置账号；默认不查看普通用户聊天内容 |

> 推荐不设置“只读访客 guest”角色；如后续确有只读展示需求，可作为扩展角色补充。

## 5. 数据模型设计

### 5.1 新增用户表 `app_user`

建议结构：

```sql
CREATE TABLE IF NOT EXISTS app_user (
    user_id        BIGSERIAL PRIMARY KEY,
    username       VARCHAR(64)  NOT NULL UNIQUE,
    display_name   VARCHAR(128) NOT NULL,
    password_hash  VARCHAR(255) NOT NULL,
    role           VARCHAR(16)  NOT NULL DEFAULT 'member'
                   CHECK (role IN ('admin', 'member')),
    status         SMALLINT     NOT NULL DEFAULT 1, -- 1 启用，0 禁用
    created_at     TIMESTAMP    NOT NULL DEFAULT now(),
    last_login_at  TIMESTAMP    NULL
);
CREATE INDEX IF NOT EXISTS idx_app_user_username ON app_user (username);
```

约束说明：

- `username` 唯一、小写规范后存储；不区分大小写。
- 不保存明文密码，只保存哈希。
- `status=0` 时禁止登录，并拒绝现有有效登录态访问。

### 5.2 新增登录会话表 `auth_session`

建议使用不透明随机令牌，数据库只存哈希：

```sql
CREATE TABLE IF NOT EXISTS auth_session (
    token_hash CHAR(64)      PRIMARY KEY, -- SHA-256(随机令牌)
    user_id    BIGINT        NOT NULL REFERENCES app_user(user_id) ON DELETE CASCADE,
    expires_at TIMESTAMP     NOT NULL,
    revoked_at TIMESTAMP     NULL,
    created_at TIMESTAMP     NOT NULL DEFAULT now(),
    user_agent TEXT          NULL,
    client_ip  VARCHAR(64)   NULL
);
CREATE INDEX IF NOT EXISTS idx_auth_session_user ON auth_session (user_id);
```

说明：

- 登录成功后后端生成随机 token，通过 HttpOnly Cookie 下发给浏览器。
- 服务端数据库只保存 `token_hash`，降低数据库泄露后的令牌泄露风险。
- 登出、改密、账号禁用时吊销对应会话；过期令牌自动拒绝。

### 5.3 现有表改造

#### `chat_session`

新增归属字段：

```sql
ALTER TABLE chat_session ADD COLUMN user_id BIGINT NULL;
-- 数据回填完成后再补 NOT NULL 与外键
ALTER TABLE chat_session ADD CONSTRAINT fk_chat_session_user
    FOREIGN KEY (user_id) REFERENCES app_user(user_id) ON DELETE CASCADE;
CREATE INDEX IF NOT EXISTS idx_chat_session_user_time
    ON chat_session (user_id, session_id DESC);
```

设计要求：

- `create_session(user_id, name)` 必须写入当前用户 ID。
- `list_sessions(user_id)` 只返回该用户会话。
- `get_session_for_user(session_id, user_id)` 返回 `None` 或 403/404；普通用户不能直接猜测 `session_id` 访问他人会话。

#### `chat_record`

- 不直接冗余 `user_id`；用户隔离通过 `session_id -> chat_session.user_id` 保证。
- 删除会话时仍按现有事务先删记录、再删会话。

#### `document` / `document_chunk`

- **不新增 `owner_id`，不做用户隔离**。
- 向量检索、Rerank、来源引用继续对所有登录用户开放。
- 文档维护接口由后端角色校验保护。

### 5.4 可选审计表 `operation_log`

建议只记录管理操作与权限操作，不记录聊天问答内容：

```sql
CREATE TABLE IF NOT EXISTS operation_log (
    log_id         BIGSERIAL PRIMARY KEY,
    actor_user_id  BIGINT NULL,
    action         VARCHAR(64)  NOT NULL, -- DOC_UPLOAD/DOC_DELETE/REPARSE/REINDEX/USER_MANAGE/AUTH_LOGIN
    target_type    VARCHAR(32)  NULL,
    target_id      VARCHAR(64)  NULL,
    result         SMALLINT     NOT NULL, -- 1 成功，0 失败
    detail         JSONB        NULL,
    created_at     TIMESTAMP    NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_operation_log_actor ON operation_log (actor_user_id);
CREATE INDEX IF NOT EXISTS idx_operation_log_created ON operation_log (created_at DESC);
```

## 6. 认证与安全设计

### 6.1 推荐认证方案：服务端不透明 Cookie Session

对比：

| 方案 | 优点 | 缺点 | 本项目建议 |
| --- | --- | --- | --- |
| Cookie + 服务端会话表 | 易服务端吊销、服务端可控、无复杂 JWT 密钥轮换 | 需要服务端存储会话 | **推荐** |
| JWT Bearer Token | 无状态、易扩展到多服务 | 吊销较复杂、易过期处理混乱、需前端统一携带 Header | 暂不采用 |

Cookie 建议：

- 名称：`rag_session`。
- `HttpOnly=true`：禁止前端 JS 读取，降低 XSS 窃取风险。
- `SameSite=Lax`：降低 CSRF；本地 HTTP 下不强制 `Secure`，未来 HTTPS 部署时增加 `Secure=true`。
- 有效期：建议 7 天；活动滑动续期；登出立即吊销。

### 6.2 密码安全

- 密码哈希推荐使用 `bcrypt`，成本因子 12 左右；不使用明文或可逆加密。
- 登录失败返回统一提示“用户名或密码错误”，避免枚举用户名。
- 可追加简单限流：同一用户名/IP 在短时间内多次失败后短时锁定；初版可只记录失败审计。
- 不把密码写入日志、响应体或前端存储。

### 6.3 后端鉴权中间层

建议新增 FastAPI 依赖：

- `get_current_user`：从 Cookie 解析 token、校验有效期与吊销状态、加载用户并检查 `status=1`；失败返回 40101。
- `require_admin`：在 `get_current_user` 基础上检查 `role == 'admin'`；失败返回 40303。
- 所有写接口与受保护查询接口接入依赖；SQL 仍集中在仓储层，路由不拼 SQL。

### 6.4 前端安全边界

- 前端根据 `role` 隐藏管理按钮、隐藏管理员页面；这只是体验优化。
- 后端必须独立校验；即使直接请求 API，member 也不能调用 admin 能力。
- axios 响应拦截器统一处理 401（回到登录态）与 403（提示无权限）。

## 8. 前端设计草案

当前前端无 `vue-router`，初版建议避免引入路由框架，采用“登录态 + 条件渲染”。

### 8.1 视图结构

1. **未登录**：只显示 `LoginView`，输入用户名/密码登录。
2. **普通用户登录后**：
   - 顶部显示用户名与退出按钮；
   - 主体为聊天页；
   - 不渲染文档管理入口。
3. **管理员登录后**：
   - 具备普通用户全部能力；
   - 额外显示文档管理入口与操作按钮；
   - 用户管理页面可作为后续扩展，初版可用命令行创建账号。

### 8.2 会话列表

- 进入聊天页只调用 `list own sessions`。
- 切换会话时若本地选中的 `session_id` 不属于当前用户，立即清空并刷新。
- 删除会话仅刷新本人列表，不影响他人数据。

### 8.3 API 客户端调整

- `api/auth.js`：登录、登出、当前用户、修改密码。
- `api/chat.js`：会话创建/列表/删除/重命名绑定当前用户。
- `api/docs.js`：调用结构不变；调用失败 403 时提示“无管理权限”。
- HTTP 拦截器：
  - 401：清除前端用户状态、进入登录视图；
  - 403：弹出无权限提示；
  - 业务错误继续沿用现有 `{code,msg,data}` 包络。

## 9. 数据迁移与兼容策略

### 9.1 新项目初始化

`init_db.sql` 最终应包含：

- `app_user`；
- `auth_session`；
- `chat_session.user_id` 及外键/索引；
- 可选 `operation_log`。

### 9.2 现有数据库迁移

单独提供迁移脚本，避免改动首次初始化逻辑：

1. 创建新表与索引；
2. 新增 `chat_session.user_id`（先允许 NULL）；
3. 创建初始 admin 账号；
4. 将历史会话回填到初始 admin；
5. 校验无 NULL 后补外键约束；
6. 不修改 `document/document_chunk`；
7. 记录迁移前后表计数，便于回滚核对。

### 9.3 历史数据处理建议

- 历史 `chat_session/chat_record`：推荐归属初始 admin，避免公开遗留会话被任意用户看到。
- 历史文档：保持全局公用，不迁移 ownership。
- 本地测试数据库测试完成后，仍需保证演示基线不受污染；迁移脚本必须幂等、可重复执行。

## 11. 验收用例草案

### 11.1 功能用例

1. member A 登录后创建会话并提问；member B 登录后列表中看不到 A 的会话。
2. member B 直接请求 A 的会话详情或删除接口，后端返回 40303 或 40402，不能泄露内容。
3. member A 与 B 对同一问题检索，返回同一套公共知识库来源。
4. admin 可上传、删除文档，可执行重解析与索引重建。
5. member 调用上传、删除、重解析、重建索引接口，后端返回 40303。
6. 禁用用户无法登录；其未失效 token 访问受保护接口被拒绝。
7. 登出后 Cookie 对应 token 被吊销，不能继续访问。
8. 管理员可重置 member 密码；member 可修改自己的密码。

### 11.2 安全与回归用例

1. 数据库中不得出现明文密码。
2. 所有管理接口必须经过 `require_admin`，不能只靠前端隐藏按钮。
3. SSE 流式生成前先完成会话归属校验，避免先产生回答再拒绝。
4. 现有 `pytest tests -q`、`check_env.py`、前端 `npm run build` 保持绿色。
5. 测试临时账号与会话测试结束后清理；生产演示数据库基线不被污染。

| D6 | 密码修改 | member 可改本人密码，admin 可重置他人密码 | 是否不开放自助改密 |

| D8 | 运行时配置 UI | 模型、切片、检索阈值仍走 `.env`/配置文件，不做 UI 编辑 | 是否要管理员页面改少量运行参数 |
| D9 | 密码哈希库 | 直接使用 `bcrypt` | 是否倾向 `passlib` 封装 |
| D10 | 批量上传角色 | admin 专属；member 不可上传 | 是否允许 member 个人上传私有文档（与“知识库公用”冲突，不推荐） |

## 13. 风险与边界提示

1. **不要把知识库私有化**：本方案 `document/document_chunk` 保持全局共享，否则会改变检索语义并增加迁移复杂度。
2. **不能只做前端隐藏**：必须在 FastAPI 依赖层做认证与角色校验。
3. **SSE 链路需前置校验**：聊天接口必须在生成内容前确认会话归属。
4. **迁移需谨慎**：历史会话回填前必须备份或在测试库演练；脚本幂等且可核对计数。
5. **本设计不包含 UI 美化、复杂权限和外部账号体系**；后续如扩展需重新评审。
6. **当前项目未引入路由框架**：P3 优先用条件渲染实现，避免为本期引入 vue-router/Pinia。

## 14. 下一步建议

评审通过并确认 D1–D10 后，再输出详细技术方案与排期；建议先从 **P1 认证基础 + P2 会话私有** 开始，先保证“登录后会话不串号、普通用户不能管理知识库”这两条核心边界。

| 编号 | 决策点 | 结论 |

### 15.2 与评审稿的差异

1. **密码哈希**：由 bcrypt 改为标准库 PBKDF2-SHA256，理由是不新增第三方依赖、部署面更小；如需切换为 bcrypt，只需替换 `services/security.py` 的 `hash_password/verify_password` 并在登录时按前缀升级。
2. **SSE 路径**：沿用既有 `POST /api/chat/stream`（评审稿写的是 `/api/chat/chat`），未改名以免破坏前端与既有脚本。
3. **`GET /api/docs/list`**：评审稿权限矩阵未明确，落地按“管理员视图”处理为 admin 专属；member 不需要文档列表。
4. **登录失败限流**：未实现，仅记录失败审计（评审稿标为初版可选项）。
5. **用户管理 UI**：初版暂缓，随后在 V57 补齐（管理员菜单「用户管理」：列表 / 新建账号 / 启禁用 / 重置密码）。
